# 抖音本地生活推荐 Agent：调研结论与方案草案

2026-10-17，第三轮更新。原始调研在同目录 01–10。本文件是合成结论，供内部讨论和跟导师对齐。

已定（用户 2026-10-17）：运行时用本机 Coze Studio；深圳建库；Stanford/yf_dianping 只做内部演示并注明；抖音开放平台账号已注册、认证中；持续学习做 SAGER 每用户策略，错题本可选；GEPA 由我决定引入与否；测试期模型随意，README 写支持豆包。

## 1. 平台与编排

### 1.1 为什么是本机 Coze Studio

老师的 12 条全是旧版低代码扣子的功能，官方原文"扣子开发平台（低代码）不再向新注册用户开放"。三条线对照（细节见 01、04）：扣子编程 AI 智能体切分不可配、记忆库不支持、只能发布为 API；新版 Coze Agent 文档里没有知识库和工作流；本机 Coze Studio 知识库三类、切分可配、混合检索加 rerank、意图识别和问答节点、高德和博查内置。缺的两样（长期记忆、召回测试）自己做。发布到抖音在任何线路上个人都做不了（只剩抖音小程序渠道，要企业主体），改 Chat SDK 网页 demo，消息类型支持 card。

模型：Coze Studio 按 .env 配模型，OpenAI 协议和火山方舟模板都有，所以"支持豆包"是真的。注意两点：单智能体模式要求模型支持 function calling，不支持直接报错；OpenAI 模板的 json_mode 写的是 false，JSON 输出靠 Prompt 加代码节点解析。

### 1.2 编排：对话流做主干，节点内用工具

Coze Studio 实际只有两条运行路径（07 第 1 条）：

| 模式 | 机制 | 适合 |
|---|---|---|
| 单智能体 | eino ReAct Agent，插件/工作流/知识库/数据库全部注册为 tool，模型自己选 | 工具少、路径不固定 |
| 对话流模式（WorkflowMode） | 整个智能体由一条对话流驱动，开始节点带 USER_INPUT，问答节点中断后 `requires_action` 自动续接，支持流式输出 | 流程固定、要可控 |

多 Agent 模式只在 api/model 层有枚举，domain 层没实现，不用考虑。

选对话流做主干，理由：
- 老师的工作流本身就是固定管线（意图识别→参数提取→推荐生成→格式化），对话流一一对应，每个节点的输入输出都能单独测。
- 弱模型做 ReAct 选工具不稳；对话流把路由交给意图识别节点和选择器，模型只在节点内做局部决策。
- 对照证据：Cognition 2026-04《Multi-Agents: What's Actually Working》结论是写操作保持单线程；Stanford 2604.02460 固定算力下单 Agent 持平或优于多 Agent。高德的主从 Agent 三层架构是为上百个工具设计的，我们只有 6 个左右的工具。

动态部分放在节点内：推荐生成那个 LLM 节点挂高德插件（LLM 节点 FCParam 支持挂插件/工作流/知识库），让它在需要时自己查距离，这是"单线程主干 + 局部工具调用"。

定时任务：Coze Studio 没有 cron，异步归并由 bridge 脚本定时调 `/v1/workflow/run`。

### 1.3 代码节点约束

只支持 Python；第三方库白名单只有 httpx 和 numpy；默认 local runner（venv 无隔离），sandbox 模式下网络默认只放行 cdn.jsdelivr.net；超时 60s、内存 100MB。READAR 时验证过输入约 100KB 上限。所以重计算（数据清洗、评测）放 bridge 脚本，代码节点只做轻量裁剪和规则判断。

规模：约 3000 门店、真实评论 2.5–3 万条、合成评论不超过真实数量、合成团购 6–9 千条。高德调用总量 1500 次/月以内。

### 2.2 抖音侧的边界

能用的：视频搜索 API；POI 关键词搜索 `poi.search` 是"定向开放媒体行业，其他行业可申请"，可以试申。
不能用的：网页端内部接口有 a_bogus 签名，用户协议 5.1、5.3(4) 明文禁止自动化采集，5.3(6) 禁止用于统计热词和分类；2025-10-15 施行的新反不正当竞争法第 13 条专门规制绕过技术措施取数据。浏览器登录后小规模手工采集在民事上风险低，但违约确定成立，而且账号会被封。结论：不碰抖音网页和 App 接口，PRD 里写清数据边界。这一条可以单独跟导师讲。

## 3. 架构

```
用户消息（对话流开始节点）
 → 反馈判定（Jev choice：接受 / 否决 / 中性，对上一轮推荐）→ 写反馈事件
 → 意图识别（Jev choice 六类 + noul "需要澄清"；LLM 版做对照）
 → 参数提取（LLM，JSON）：位置、品类、人均、人数、时间、距离上限、口味禁忌
   输入 = 当前消息 + 会话状态 JSON + 用户长期画像摘要，不喂全量历史
 → 槽位检查（代码）→ 缺关键槽位或意图置信低 → 问答节点（早期问属性，后期问具体店）
 → 结构化召回（数据库 SQL：品类、人均区间、评分下限、营业中）→ 最多 20 家
 → 候选预筛（Jev score "符合约束程度"，留前 8）
 → 证据召回（知识库向量检索评论/套餐，按门店 id 过滤）→ 证据筛选（Jev noul "支持用户条件"，每店留 3 条）
 → 推荐生成（LLM，挂高德插件查距离）：输入候选裁剪后字段 + 证据 + 画像 + 用户策略文本，输出带 matched_criteria
 → 格式化（卡片；对比意图走固定维度 PK 卡）
 → 记忆写入（Jev 四选一 + 长期稳定性判定；短期：会话状态表；长期：画像表、策略文本，异步归并）
```

Jev 节点都有 LLM 后备（同一 schema，HTTP 节点只换 base URL），每个决策点先 LLM 跑通再换 Jev 做 shadow 对比，见 3.7。

### 3.1 context engineering 怎么落到节点

依据：Anthropic 2025-09《Effective context engineering》、Manus 2025-07、Chroma《Context Rot》、Google ADK 2025-12（07 第 8 条）。

| 原则 | 本项目的做法 |
|---|---|
| working context 每轮重建，不滑动窗口（Google ADK；Chroma 实测聚焦提示 300 token 优于全历史 113k） | 每个 LLM 节点输入是编译好的视图：会话状态 JSON + 画像摘要 + 本轮候选。chatHistoryRound 设 2，不靠历史轮数记状态 |
| structured note-taking（Anthropic） | 会话状态存变量/数据库表，不存对话原文 |
| 工具输出 token-efficient | 高德返回的大 JSON 经代码节点裁到 id、名称、距离、时长；SQL 返回 20 家只留 6 个字段 |
| progressive disclosure / just-in-time | FAQ、榜单知识库不自动召回（Auto=false），只在对应意图分支里显式检索 |
| 稳定前缀利于 KV cache（Manus） | 系统提示词静态，动态内容放末尾 |
| 单个干扰项就降性能（Chroma） | 证据召回按门店 id 过滤，不把其他店的评论混进来 |
| Keep the wrong stuff in（Manus） | 节点内 FC 重试时保留上一次错误返回，不清空 |

### 3.2 长短期记忆分层

- 短期：会话状态表（conversation_id 为键：槽位、候选列表、轮次、本轮反馈）。Coze Studio 的变量按用户隔离不按会话，所以会话态走数据库表，会话开始时清。
- 长期：画像表（uid、偏好类型、值、支持次数、最近出现、一致性）。写入由 LLM 四选一 ADD/UPDATE/DELETE/NOOP（Mem0，2504.19413）。
- 短期提升为长期的两个信号借 MATE（2610.06050）：同一偏好历史重复次数、最近几次是否一致。"今天想吃辣"只进短期。
- 归并异步：bridge 脚本定时调工作流做"睡眠期"整理（LightMem 2510.18866；Claude Managed Agents 2026-05 的 Dreaming、ChatGPT 2026-06 的 Dreaming 是同一思路的工业落地）。
- 评测：30–50 条 LongMemEval 风格"知识更新"用例，检查画像表终态。

### 3.3 持续学习：每用户策略文本 + 全局错题本

不动模型权重，从使用中学（细节见 08）。只选两层：

1. **每用户策略（必做）**：SAGER（2604.14972，2026-04）。每个用户一段自然语言"推荐策略"，用"被接受的店 vs 未选的店"做对比式改写。Yelp 上 H@1 0.487→0.523（自报 +7.4%），gpt-4o-mini 就够。信号本项目天然有：用户点"就这家"或问路线算接受，换方向算否决。实现是一张用户表加一个 LLM 改写节点。
2. **全局错题本（可选）**：失败对话（连续追问、用户换方向）按批聚类成规则条目，只在批次评测提升时写入（Mistake Notebook Learning 2512.11485），按效用淘汰（Darwinian Memory 2601.22528）。这和 ACE 的 playbook 是同一类，取其一。

不做：Training-Free GRPO（弱基座有负收益记录，QwQ-32B 27.5→25.5）、Memory-R1、任何需要训练的方法；JEPA 类世界模型与本项目无关。GEPA 保留为离线 Prompt 优化（3.5）。

离线评测可以用真实数据：Stanford 数据里同一用户有多条评论，留出最后一条，看策略文本是否提高命中，待验证用户字段是否可用。

### 3.4 知识库召回（对应"测召回、优化切分"）

- 门店硬条件（价格、评分、距离、营业时间）走数据库 SQL，向量库只放评论、套餐描述、FAQ。依据 Text2VectorSQL（2506.23071）；本机表格知识库靠 NL2SQL 且无列过滤参数，不适合硬过滤。
- 评论切片前由脚本补"店名 | 商圈 | 品类 | 评分"前缀（Contextual Retrieval，自报 top-20 失败率 5.7%→2.9%）。
- 切分对照：自动 / 固定 300 字 / 按评论条 / 按评论条加前缀（2603.06976 的 36 种策略评测里段落组最优）。
- 召回测试平台没有，bridge 脚本做：100–200 条带金标门店的查询，调知识库检索接口算 recall@5、MRR。

### 3.5 Prompt 优化

手写版先上。标注集 200 条：从 DuRecDial 2.0 的美食、餐厅域对话改写一部分，其余由 LLM 生成，人工抽查 30 条。DSPy 的 GEPA（2507.19457）只优化意图识别和槽位提取两个节点，与手写版对照报数。2603.25169 发现 GEPA 多数不显著优于专家手写，所以两版都报。意图节点如果换成 Jev，GEPA 改为优化 Jev 问题的 instructions 和 criteria 文本。

### 3.6 插件清单与异常处理

| 插件 | 来源 | 用途 |
|---|---|---|
| 高德地图 | 内置，9 个接口 | 周边搜索、地理编码、路线、距离、IP 定位 |
| 博查搜索 | 内置，约 0.036 元/次，赠 1000 次 | 媒体稿、榜单、实时信息，结果按天缓存进数据库 |
| 抖音视频搜索 | 自定义插件，OpenAPI 导入 | 热门内容、内容热度 |
| 节假日/日期 | 自定义 HTTP 或代码节点 | "周末""节假日"槽位归一化 |

异常处理按 ToolBench-X（2606.25819）五类故障各留一条路：高德超时或空结果→数据库缓存坐标算直线距离；搜索空返回→静态榜单知识库；JSON 解析失败→节点异常分支返回默认 JSON；配额用尽→切百度地点检索（个人 100 次/日）。HTTP 节点 `settingOnError` 和 LLM 节点超时重试已验证可用。

### 3.7 决策层：Jev（System One 决策模型）

细节与出处见 09。Jev 是 TypeSafe AI 2026-09-15 发布的决策模型，不生成文本，输入状态加类型化问题（choice / score / noul），输出带概率的类型化答案，自报延迟 70–500ms、输入 $0.042/MTok 输出免费，闭源。注册 09-27 重开，无免费额度。中文官方说"支持但精度不一"；第三方 jev-study 的中文分类、讽刺、双重否定全对但样本是手工构造；Chinese-Jev（2609.36965）自报中文通用域比 Jev 高 1.24%，权重未确认开源。

引入理由：管线里有七个"有限答案集合"的判断（意图、是否澄清、反馈正负、记忆四选一、长期稳定性、证据相关、候选符合度、插件故障类别）现在都要用 LLM 生成再解析，Jev-LiteMAS（2610.21411）测得这类路由和审核占多 Agent 生成 token 的 31.7%–43.5%。Jev-Mem（2609.23986，代码 MIT）把记忆的类型打分、关系建边、巩固四选一、检索路由和自适应停止全交给 System One，LoCoMo 0.777 对 MAGMA 0.700、A-MEM 0.580，构建时间 158 秒对 3636 秒，可以直接照它的阈值设计记忆写入（merge/promote ≥ 0.85 才让 LLM 写摘要）。

落地：Coze Studio 没有 Jev 节点，用 HTTP 节点或 OpenAPI 导入的自定义插件调 `/v1/systemone`。后备是 bridge 侧起一个同 schema 的 LLM-as-Jev 服务（2610.02076：候选编号后读 logprob 做 softmax，Qwen3.5-4B 零样本 JevBench 81.4%），本机 Ollama 的 qwen 就能跑，中文无问题。Kev（开源克隆，9.3k star）只支持英文且 4B 要 16GB 显存，本机无 GPU，不用。

评测：每个决策点用 200 条标注做 Jev 与 LLM 的准确率和校准曲线对比，顺序置换检查偏置。这组对比本身是一个可写的实验。

风险：闭源早期访问、中文无第三方准确率、不能抽槽位、账号和充值要用户办。

### 3.9 从同类产品补进来的功能

探饭、小美、小高老师、Ask Maps、Yelp 等 11 个产品的功能对照见 10。低成本且有依据的四项加进 PRD：

- 多店 PK 卡（探饭）：固定维度（场景、特色、推荐菜、人均、距离、优劣势），对应"对比评价"意图。
- 人数 + 预算 + 忌口→整桌方案（探饭、点仔）：参数提取加字段，套餐数据配合。
- 匹配条件打勾式解释（Yelp）：推荐生成输出 matched_criteria，卡片上逐条打勾。
- 停车、包间、儿童椅等属性过滤（Ask Maps、小高老师）：高德 POI 属性字段，合成补齐并标注。

差异化候选（公开稿里没人做）：多人聚餐偏好合并（每人画像取交集再排序）。预订、排队时长、支付闭环需要商家接口，不做。
